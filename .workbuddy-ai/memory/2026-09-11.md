# 2026-09-11 (later) — trip search + greeting fixes

Two reported issues: the dashboard greeting was unreadable, and trip search
appeared to do nothing. Both turned out to have concrete, verifiable causes.

## Root cause 1 — `ApiService` never called `fromJson`

`ApiService.get<T>` accepted a `T Function(dynamic)` transform and **silently
ignored it**, calling `_dio.get<T>` directly. Every fleet endpoint wraps its
payload as `{Success, Message, Data:{…}}`, so asking Dio for `List<dynamic>`
could not cast the enveloped `Map`. Dio raised `DioException(unknown)`, which
`_handleDioException` mapped to the generic *"Network error. Please check your
connection."* with `statusCode: null` — and because the status was null,
`_getList` swallowed it and fell through to a 404 fallback route, so the error
the user actually saw was a misleading upstream 404.

Proven with a probe: `api.get('/trips/locations')` returned the envelope Map,
while `api.get<List<dynamic>>(…)` threw `ApiException: Network error`.

**Fix**: `_send`/`_attempt` now execute every request untyped and apply the
transform via `_resolve<T>`, which throws a *descriptive* `ApiException` when
the shape genuinely doesn't match.

## Root cause 2 — envelope unwrapping looked at the wrong level

`_asList` only searched for list keys on the **top level**, so
`{Data:{Locations:[…]}}` returned `[envelope]` — one garbage row instead of
three real locations. Routes worked by accident because their `Data` *is* the
list. Extracted into `lib/utils/api_envelope.dart` (`ApiEnvelope`) so it is
unit-testable; `{Data: null}` now correctly means "no rows", not "one row".

## Root cause 3 — the user's bearer token broke the public catalog

`loadCatalog`/`searchTrips` forwarded the logged-in user's token. The fleet
catalog is a **store-scoped public read** (X-Api-Key + apiKey/storeId) and the
upstream rejects a stray `Authorization` header — curl: **401 with a token,
200 without**. With no locations, `canSearch` stayed false and the Search
button stayed disabled: exactly "nothing happens when I click search".

**Fix**: the catalog calls no longer forward the token, *and* `ApiService._send`
retries once without the token on 401/403 as a general safety net. Verified
live: `getLocations(authToken: 'stale-token')` → logs
`API retry: /trips/locations rejected the bearer token (401); retrying without it`
→ returns all 3 locations.

## Dashboard greeting

`Lux.heroOverlay` is **fully transparent for its first 35%**, and the greeting
sat at the very top of the hero — so it rendered straight onto the photograph
with no scrim at all. Added `Lux.heroScrim` (dense band at the top, opening
mid-frame, closing again at the bottom) plus `Lux.heroTextShadow`, and moved
the header into a reusable `lib/widgets/premium_hero_header.dart`
(greeting 21px→28px, w600→w700, subtitle 72%→92% opacity).

## Test-environment trap (important)

**`testWidgets()` replaces `HttpClient` with a mock that answers 400 with an
empty body for every request.** A widget test can therefore never talk to the
real backend. `test()` in a file with no `testWidgets` uses the real client.
This made the dashboard repro test look like it was getting a 400 from the API
when it was actually the Flutter test mock. Real network checks must live in
plain `test()` files (see `test/live_api_probe_test.dart`, which skips itself
when the proxy is down).

# 2026-09-11 (later still) — Render deployment prep

Goal: one public URL serving the Flutter web app **and** the API proxy from a
single origin, deployable to Render's free tier.

## Architecture decision

**Single Node service, zero npm dependencies.** `server.js` does both jobs:
serves `swift-fleet-api/public/` as static files and reverse-proxies `/api/*`
to `https://ecomapi.swift.ng`. Because client and API share an origin, the
Flutter app calls a **relative** `/api/fleet` path — no CORS preflight, no
hardcoded host in the bundle. Zero deps means Render needs no `npm install`,
so cold starts stay fast on the free tier.

## Files created / rewritten

- `swift-fleet-api/server.js` — rewritten as the unified static + proxy server.
  Router: `OPTIONS`→204, `/health`+`/healthz`, `/api/*`→proxy, non-GET/HEAD→405,
  else static. Manual gzip with a small `path:mtimeMs` cache
  (`main.dart.js` 3.99 MB → 1.19 MB). Path-traversal guard in
  `resolveStaticPath`. `HOP_BY_HOP` header filter both ways. 30 s upstream
  timeout, 502 JSON on upstream failure, SIGTERM/SIGINT graceful shutdown.
- `swift-fleet-api/package.json` — `start: node server.js`, `engines >=18`,
  `dependencies: {}`.
- `swift-fleet-api/scripts/build-web.js` — cross-platform (Node + `fs` only)
  `flutter build web --release --output swift-fleet-api/public`, with pre/post
  flight checks. Uses `flutter.bat` + `shell: true` on Windows.
- `package.json` (repo root) — thin wrapper so Render detects a Node service at
  the root: `start: node swift-fleet-api/server.js`.
- `scripts/render-build.sh` — clones a pinned Flutter SDK to `$HOME/flutter`,
  `pub get`, builds web into `swift-fleet-api/public`.
- `render.yaml` — one `web` service, `runtime: node`, `plan: free`, health check
  `/health`, `API_KEY` with `sync: false`.
- `DEPLOY.md` — full runbook (Option A build-on-Render vs Option B prebuilt).
- `.gitignore` (+ `swift-fleet-api/.gitignore`) — deployment section.

## Key design choices worth remembering

- **Service root must be the repo root**, not `swift-fleet-api/` — Render has to
  see `pubspec.yaml` *and* the server. Hence the root `package.json` wrapper.
- **Server-side credential injection.** The proxy *overwrites* `apiKey`/`storeId`
  and sets `X-Api-Key`, so the deployed client never carries the real key and
  rotation needs no rebuild.
- **SPA fallback only for extension-less paths.** `/trips` → `index.html`;
  `/missing.js` → real 404, so build mistakes stay visible instead of being
  masked by HTML.
- **`flutter build web --output`** is used because `/build/` is gitignored and
  would never reach Render.
- **`Accept-Encoding: identity`** on upstream requests to avoid double
  compression (we gzip ourselves).

## THE ONE REAL RISK

`flutter build web` needs **~2 GB RAM**; Render's free tier gives **512 MB**.
So Option A (build on Render) will likely OOM. **Recommend Option B**: build
locally, commit `swift-fleet-api/public/`, and switch the build command to
`npm install --omit=dev`. `render.yaml` documents the exact swap.
